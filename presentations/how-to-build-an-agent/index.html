Agent 的四个功能模块

感知 Perception

接收用户输入、工具返回、文件内容和系统状态，把外部信息整理成模型能理解的上下文。

推理 Reasoning

分析当前状态，拆解任务，判断下一步应该继续收集信息、调用工具，还是结束回答。

行动 Action

调用 API、查询数据库、执行脚本；模型输出结构化指令，程序负责执行并回传结果。

记忆 Memory

保存短期上下文、中间结果和长期知识，让 Agent 不必每一步都从零开始。

Chapter 1

四个能力来自上下文工程

四个能力先落在上下文里。后端把系统规则、技能说明、历史记忆、可用工具和用户输入打包成同一份文稿，再交给模型判断下一步；用户输入只是其中很小的一段。

机制本身并不神秘。Agent 没有改写模型内部运行方式，而是在模型外部组织上下文、调用工具、接回结果，再把下一轮上下文继续补齐。

Chapter 2 / 初识 ReAct

ReAct：现代 Agent 的起点

2022 年的一篇论文，定义了 Agent 的基础范式

ICLR 2023
ReAct: Synergizing Reasoning and Acting in Language Models
Shunyu Yao (姚顺雨) · Jeffrey Zhao · Dian Yu · Nan Du · Izhak Shafran · Karthik Narasimhan · Yuan Cao
Princeton University · Google Research (Brain Team)
arXiv: 2210.03629 · 2022.10.06

论文解决了什么问题

在 ReAct 之前，语言模型的推理和行动是两条独立研究线：

Chain-of-Thought

让模型把推理过程写出来，"多想几步"。但模型的推理没有外部信息反馈，容易跑偏、产生幻觉。

Tool Use

让模型调用外部工具，"动手去查"。但缺乏推理过程，模型不知道何时该查、查完怎么分析。

ReAct 第一次把二者拧成了一个交替循环——先想一步、再调一个工具、看到结果再想下一步。这个循环骨架就是今天几乎所有 Agent 的基础。

历史地位：后来所有的主流 Agent 框架（AutoGPT、LangChain Agent、OpenAI Function Calling、Claude Tool Use）本质上都是 ReAct 循环的工程化实现。第一作者姚顺雨后来成为 AI Agent 领域的标志性人物，于 2025 年底加入腾讯担任首席 AI 科学家。
Chapter 2

ReAct 模式

ReAct = Reasoning + Acting，是构建 Agent 最经典也最直观的基础模式。它的核心是一个循环：

🧠 Thought
推理下一步
→
🔧 Action
执行工具调用
→
👁 Observation
观察执行结果
→
✅ 结束
输出最终答案

循环直到得出最终答案，或达到最大步数限制

为什么需要这个循环

单次 LLM 调用能做的事很有限：它只能基于训练数据生成文本，没有实时信息，不会算复杂数学，不能操作外部系统。ReAct 循环把一个大任务拆成多步，每一步模型只做一次推理、调一个工具，用工具的返回值弥补自身能力的缺口。

具体例子

用户：今天北京天气怎么样？适合跑步吗？ Thought: 需要查北京天气和 AQI，先查天气 Action: 调用 get_weather(city="北京") Observation: 晴，18°C，湿度 45%，风力 3 级 Thought: 天气不错，再查空气质量 Action: 调用 get_aqi(city="北京") Observation: AQI 52，PM2.5=22，级别：良 Thought: 得到了足够信息，可以回答了 Final: 北京今天晴天 18°C，AQI 52（良），非常适合户外跑步。
Chapter 4

动手实现

整个 Agent 的核心循环不超过 30 行代码。骨架长这样：

async function runAgent(userMessage: string) { const messages = [systemPrompt, { role: "user", content: userMessage }]; for (let i = 0; i < MAX_STEPS; i++) { const response = await llm.chat(messages, tools); if (response.finishReason === "stop") { return response.content; // 模型认为可以结束了 } if (response.finishReason === "tool_calls") { for (const call of response.toolCalls) { const result = await executeTool(call.name, call.args); messages.push({ role: "tool", tool_call_id: call.id, content: result }); } // 把执行结果追加到上下文，继续下一轮循环 } } return "达到最大步数限制，任务未完成。"; }

三个实现要点

  • 工具描述决定调用质量 — 模型选哪个工具、传什么参数，唯一依据就是 Tool Schema 里的文字描述。描述写查询天气和写输入城市名返回温度湿度风力，模型的调用准确度完全不同。参数尽量带约束，enum 和 required 是最低成本的防错手段。
  • 用 Prompt 教模型先想再做 — ReAct 论文的关键发现是模型不需要微调，只要在 System Prompt 里放一两个完整的推理后调用工具再观察结果的示例，模型就会模仿这个交替模式。你的 Prompt 里有没有这个范例，决定了模型会不会先分析再行动。
  • 错误不要中断循环 — 工具超时、参数非法、返回解析失败，把这些错误信息原样写回 messages 数组，让模型在下一轮推理中看到失败原因，自己判断是换参数重试还是换一个工具。在 ReAct 循环里错误不是异常，是 Observation 的一部分。
